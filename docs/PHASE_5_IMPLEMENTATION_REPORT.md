## Executive Summary

Phase 5 transitions the PredictIQ platform from offline model development to an enterprise-grade, containerized production inference service. Using **FastAPI** and **Uvicorn**, the service encapsulates the calibrated churn champion model (*RandomForestClassifier* with Platt sigmoid calibration and frozen decision threshold $p^* = 0.3400$) behind a clean REST API.

Key accomplishments:
1. **Model-Serving Integration:** Loaded persisted model pipeline (`models/churn_champion_model.joblib`) and metadata at application startup via FastAPI lifespan events without retraining. Missing artifact errors return a structured `503 Service Unavailable` response.
2. **REST API Endpoints:** Implemented `GET /health`, `GET /ready`, `GET /model-info`, `POST /predict`, and `POST /predict/batch` with Pydantic v2 schemas.
3. **Data Privacy & Security:** Sensitive identifiers (`customerID`), raw dataset samples, internal server paths, and credentials are completely excluded from responses, logs, and error messages. Interactive documentation (`/docs`, `/redoc`) is automatically disabled in production mode.
4. **Asynchronous Architecture:** Offloaded CPU-bound scikit-learn inference to worker threadpools (`starlette.concurrency.run_in_threadpool`) to prevent blocking the event loop.
5. **Comprehensive Verification:** 16 new API unit and integration tests added, bringing the total suite to **113 passing tests** (100% pass rate) with zero Ruff linter errors.
6. **Empirical Latency Benchmarking:** Single-record median latency measured at **208.24 ms** (p95: 258.77 ms). Batch inference amortizes pipeline overhead down to **4.27 ms per record** at batch size 50.
7. **Production Containerization:** Built and verified a multi-stage Docker container based on `python:3.13-slim`, running under an unprivileged user (`appuser`, UID 10001), featuring built-in healthchecks, and operating independently of PostgreSQL and MLflow.

## 1. Model-Serving Architecture

The model serving architecture enforces strict separation of concerns between API routing, request validation, and machine learning inference:

```
[ Client Request ]
       │
       ▼
[ FastAPI App (Uvicorn ASGI) ]
       │
       ├─► [ Structured Logging Middleware ] (PII-safe latency & status logging)
       │
       ├─► [ Pydantic v2 Schema Validation ] (Bounds, types, categorical checks)
       │
       ├─► [ Dependency Injection /deps.py ] (Readiness verification, 503 safety)
       │
       └─► [ Threadpool Worker ] (run_in_threadpool)
                 │
                 ▼
       [ ChurnPredictor Engine ]
                 │
                 ├─► [ Preprocessing Pipeline ] (Encoding, domain feature engineering)
                 ├─► [ Calibrated Classifier CV ] (5-fold Platt Sigmoid over 120 RF trees)
                 ├─► [ Frozen Decision Threshold ] (p* = 0.3400)
                 └─► [ Risk Tier Assignment ] (Low < 0.20, Medium 0.20–0.50, High > 0.50)
```

### 1.1 Startup Lifecycle and Zero Retraining
- The model is loaded exactly once during application startup in the FastAPI `lifespan` handler (`src/predictiq/api/app.py`).
- **No retraining occurs at API startup.** If model files are absent or unreadable, startup catches the error, marks the service as unready (`app.state.model_loaded = False`), logs a clean error message, and serves `503 Service Unavailable` for inference and readiness probes without crashing the process.
- Model logic is strictly encapsulated within `ChurnPredictor` (`src/predictiq/inference/predictor.py`); API route handlers perform zero scikit-learn or pandas transformations directly.

### 1.2 Decision Threshold and Probability Calibration
- The model uses the frozen decision threshold $p^* = 0.3400$ optimized during Phase 4 training cross-validation to maximize churn recall while maintaining precision.
- Calibrated probabilities generated by the fitted Platt sigmoid scaler are preserved.
- Risk tiers are consistently assigned:
  - **Low Risk:** Probability $< 0.20$
  - **Medium Risk:** $0.20 \le \text{Probability} \le 0.50$
  - **High Risk:** Probability $> 0.50$

## 3. Performance & Empirical Latency Measurements

Latency benchmarking was conducted locally on Windows 11 with Python 3.13.14 using `scripts/benchmark_latency.py`. A representative test suite was executed against the champion model pipeline.

### 3.1 Latency Benchmark Results

| Test Case | Sample Size | Median (p50) | 95th Percentile (p95) | Mean Latency | Min Latency | Max Latency | Per-Record Latency |
|---|---|---|---|---|---|---|---|
| **Single Record (`/predict`)** | 50 requests | **208.24 ms** | **258.77 ms** | 213.26 ms | 188.58 ms | 295.34 ms | 208.24 ms |
| **Batch ($N = 10$)** | 20 batches | **207.60 ms** | **253.22 ms** | 211.58 ms | 192.10 ms | 255.45 ms | **20.76 ms** |
| **Batch ($N = 50$)** | 10 batches | **213.30 ms** | **250.43 ms** | 217.40 ms | 195.42 ms | 258.12 ms | **4.27 ms** |

> [!NOTE]
> **Performance Transparency:**
> We explicitly state our measured median latency of **208.24 ms** and p95 of **258.77 ms** for single-record scoring. We do **not** claim sub-50ms performance for single requests. The champion ensemble consists of 5 cross-validation folds of 120 decision trees (600 trees total) evaluated across pandas DataFrames with feature transformations. However, batching amortizes this fixed ensemble overhead dramatically down to **4.27 ms per record** at batch size 50.

### 3.2 Key Inference Pipeline Optimization
During initial benchmarking, `predict_detailed()` had an execution time of ~390 ms. Investigation revealed that the pipeline was executing `predict_proba(df)` (600 trees) and then redundantly calling `predict(df)` (another 600 trees). We refactored `predict_detailed()` to compute binary churn predictions directly from the already calculated calibrated probabilities against the frozen threshold $p^* = 0.3400$, cutting median execution latency from **388.90 ms** down to **208.24 ms** (~46% latency reduction).

## 4. Containerization & Deployment

### 4.1 Production Dockerfile Design
A dedicated production Dockerfile (`Dockerfile`) was authored with the following characteristics:
- **Base Image:** `python:3.13-slim` (Debian Bookworm) for minimal attack surface and small image footprint (~304 MB compressed runtime).
- **Non-Root Execution:** Created dedicated unprivileged user `appuser` (UID 10001, GID 10001) under which the Uvicorn ASGI server runs.
- **Healthcheck Probe:** Configured container-level probe using `curl -f http://localhost:8000/health || exit 1` (interval 30s, timeout 5s, start-period 10s, retries 3).
- **Runtime Independence:** Excludes PostgreSQL and MLflow; packages only runtime requirements and model binaries (`models/churn_champion_model.joblib` and `models/churn_champion_model_metadata.json`).
- **Build Isolation:** Utilizes `.dockerignore` to prevent leaking development artifacts (`.git`, `.venv`, `mlruns`, `tests`, `data/raw`).

### 4.2 Docker Compose Integration
Updated `docker-compose.yml` to define the `api` service alongside existing optional infrastructure:
```yaml
  api:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: predictiq-api
    restart: unless-stopped
    ports:
      - "8000:8000"
    environment:
      - ENVIRONMENT=production
      - LOG_LEVEL=INFO
      - PREDICTIQ_ROOT_DIR=/app
      - MODEL_PATH=/app/models/churn_champion_model.joblib
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
```
Syntax validated successfully via `docker compose config`.

## 6. Critical Evaluation Limitation Preservation

> [!WARNING]
> **Preserved Protocol Limitation from Phase 4:**
> While the evaluation protocol was corrected in Phase 4 to drive model selection strictly from training-only 5-fold cross-validation and evaluate candidate models against a locked held-out split (Seed 2026), **the new split seed does not establish a genuinely independent test dataset**. Earlier exploratory development (Phase 3) utilized the underlying IBM Telco Customer Churn dataset. Consequently, reported held-out metrics (PR-AUC 0.6684, ROC-AUC 0.8428, F1 0.6231, Recall 71.39%) must **not** be described as an unbiased, independently validated performance estimate. Genuinely independent validation requires scoring against unobserved customer cohorts collected over a subsequent operational time window.
